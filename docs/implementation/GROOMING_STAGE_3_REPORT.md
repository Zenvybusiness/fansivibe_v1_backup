## 2. Use-Case Flow

The `CreateGroomingRun` use case (`UC-27`) follows the same pattern as `CreateHairstyleRun`:

1. **Validate grooming request** — retrieves the user's stored `style_profile` via `UserStateRepository`; raises `INSUFFICIENT_USER_DATA(422)` if `face_shape` is missing
2. **Resolve authenticated user** — `user_id` passed from the API router via dev-auth bearer token seam (`Depends(get_current_user_id)`)
3. **Retrieve required user/profile data** — `get_style_profile(user_id)` returns the `style_profile` dict with face_shape, skin_tone, body_type, style_type
4. **Build the approved grooming context** — constructs an `AppearanceProfile` from the profile data, with `sourceRunId` set to the new run's ID
5. **Create the analysis run** — inserts a new `analysis_runs` row with `run_type="grooming"`, `engine_version="rules-v1"`, `status="pending"`, `input_media=None` (profile-only pass)
6. **Persist the required context snapshot** — calls `recommend_grooming(knowledge, appearance)` which runs the full decision engine (context builder → candidate generation → filtering → scoring → ranking → explanations → confidence → recommendation)
7. **Invoke the Grooming Decision Engine** — the engine stages (DE-0) compose: context builder, candidate generation from catalog, binary filtering by excluded look IDs, weighted scoring (seed + face-shape boost + preference boost), score-descending ranking, catalog-grounded explanations, and confidence derivation
8. **Persist the grooming result** — on success, calls `runs.complete(run_id, user_id, status="completed", result=result.to_snapshot())`, storing the full result dict (appearance, confidence, needs_more_data, top + alternatives) in the `result` column
9. **Preserve historical analysis data** — each run gets a unique `run_id`; the `analysis_runs` table is append-only. Previous runs remain intact and reproducible from their stored context/result snapshots
10. **Return the appropriate run/result information** — returns `AsyncAccepted(run_id)` from the router, which the Flutter client polls via `GET /v1/analysis/runs/{run_id}`

## 3. Lifecycle Reused

The existing analysis-run lifecycle is reused exactly, with no second status system:

| Status | Transition | Notes |
|---|---|---|
| `CREATED` (implicit) | Run created with `status="pending"` | By `AnalysisRunRepositorySQL.create()` |
| `PROCESSING` | Not stored as a separate state | The run is `pending` while the engine executes; the use case doesn't set `PROCESSING` explicitly |
| `COMPLETED` | `pending → completed` via `complete_analysis_run` SQL function (TRX-5) | Guarded write-once; second call returns `false` (idempotent) |
| `FAILED` | `pending → failed` via `fail_analysis_run` SQL function (TRX-5) | Only `pending → failed` allowed; frozen `PROCESSING_FAILURE` error + `details.run_id` |

The `complete_analysis_run` SQL function guards the transition: `UPDATE ... SET status='completed', result=... WHERE id=p_run_id AND user_id=p_user_id AND status='pending'`. If the run is not `pending`, the update is silently skipped (returns `false`). This same pattern is used by `CreateHairstyleRun` and `CreateGroomingRun`.

Per the `AnalysisRun` DTO and the existing save flow contract, each completed grooming run persists:

| Field | Source |
|---|---|
| `run_id` | UUID generated by `AnalysisRows.create()` |

| `created_at` | `NOW()` at creation |

| `engine_version` | `"rules-v1"` |
| `input_media` | `None` (profile-only pass, D2) |
| `result` | `GroomingResult.to_snapshot()` dict containing: |
| &nbsp; &nbsp; `appearance` | `{faceShape, skinTone, bodyType, styleType, sourceRunId}` |
| &nbsp; &nbsp; `confidence` | float in [0, 1], derived from 50% completeness + 50% decisiveness |
| &nbsp; &nbsp; `needs_more_data` | bool, true when profile completeness < 1.0 |
| &nbsp; &nbsp; `recommendations` | `{top, alternatives}` with `id, name, description, matchScore, reasons, stylingTips, maintenance, bestFor` |
| `error` | `{"code": "PROCESSING_FAILURE", "message": "...", "details": {"run_id": "..."}}` if failed |

The persisted `result` contains everything required by the existing save flow (`POST /v1/looks/saved`): the full appearance snapshot, the top recommendation with all value-object fields (`id, name, description, matchScore, reasons, stylingTips, maintenance, bestFor`), confidence, and `needs_more_data` flag.

from app.domain.services.grooming_rules import recommend_grooming
