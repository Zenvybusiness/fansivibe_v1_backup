### 1. Executive Summary

In Stage 1D Batch 4B.3, the conversational assistant's static catalog outfit recommendation logic in `backend/app/ai/tools.py` was replaced with direct delegation to the canonical `GenerateOutfit` use case (`GenerateOutfit.derive_with_reason`).

Prior to this batch, the assistant's `recommend_outfit` tool relied on hardcoded static catalog lookups (`app_catalog.OCCASION_TO_LOOK`), hardcoded match scores (e.g., 93%), synthetic components, and an in-memory dictionary mapping simulated owned status.

With Batch 4B.3:
- The conversational assistant delegates outfit recommendation to canonical `GenerateOutfit`.
- Candidate generation, filtering, multi-term scoring, ranking, and grounded explanations are identical to the Fansivibe Outfit Builder.
- Authenticated requests resolve wardrobe items and style preferences through authoritative server PostgreSQL repositories (`WardrobeItemRepositorySQL`, `UserStateRepositorySQL`).
- Guest requests resolve wardrobe items and style preferences through in-memory ephemeral adapters (`EphemeralWardrobeItemRepository`, `EphemeralUserStateRepository`) with zero database access, zero database writes, and zero invented or sentinel UUIDs.
- Clear, typed empty and error states (`EMPTY_WARDROBE`, `MISSING_REQUIRED_CATEGORY`, `NO_LEGAL_CANDIDATE`, `DATABASE_FAILURE`) replace fabricated outfits or static catalog fallbacks.

### 2. Previous Static Recommendation Implementation

Prior to Batch 4B.3, `recommend_outfit` in `backend/app/ai/tools.py` operated as follows:
- Maintained a static dictionary of synthetic owned items:
  ```python
  _owned = {"1": True, "2": True, "3": True, "4": True, "6": True, "9": True}
  _owned_names = { ... }
  ```
- Looked up an occasion in `app_catalog.OCCASION_TO_LOOK.get(occasion, app_catalog.OCCASION_TO_LOOK["smart_casual"])`.
- Produced a hardcoded score (93%).
- Emitted hardcoded catalog components:
  ```python
  components = [f"{_owned_names.get(item_id, item_id)} (Owned)" for item_id in look.garment_ids]
  ```
- Claimed ownership for items based solely on static dictionary membership rather than the user's actual wardrobe.
- Completely bypassed canonical 12-term candidate scoring, occasion rules, palette rules, fit rules, and user-state preferences.

### 3. New Canonical `GenerateOutfit` Delegation Flow

The new implementation delegates directly to `GenerateOutfit.derive_with_reason`:

```
Assistant Request / Tool Call
              │
              ▼
   tools.recommend_outfit(...)
              │
              ├─► Resolve Dependencies:
              │   • generate_outfit: Optional[GenerateOutfit]
              │   • wardrobe_items: WardrobeItemRepository
              │   • user_state: UserStateRepository
              │   • user_id: Optional[str]
              │
              ├─► Map Inputs:
              │   • preferred_occasions: [occasion]
              │   • preferred_item_ids: [item_ids]
              │   • fit: Optional[str]
              │   • color_palette: Optional[str]
              │   • mood: (Contextual only, 0 scoring points)
              │
              ├─► Execute Canonical Derivation:
              │   GenerateOutfit.derive_with_reason(req)
              │   ├── Candidate generation across owned wardrobe
              │   ├── Strict category pairing (Top + Bottom / One-piece)
              │   ├── Multi-term scoring (occasion, palette, fit, feedback)
              │   └── Deterministic ranking & explanation derivation
              │
              └─► Map Result to SuggestionCard:
                  ├── title: rec.title
                  ├── score: int(round(rec.match_score * 100))
                  ├── subtitle: Grounded reason chain from rec.reasons
                  └── components: ["{item.name} - {item.category}"]
```

Key principles enforced:
1. **Zero Secondary Scoring**: No secondary scoring algorithm exists in `tools.py`.
2. **Canonical Explanations**: Subtitles are constructed directly from `rec.reasons` generated by `analysis_rules.py`.
3. **No Fabricated Ownership**: Garment components reflect actual wardrobe records retrieved from the repository.
4. **Deterministic Selection**: Derivation uses seed or deterministic sort ordering.

### 4. Authenticated Execution Path

Authenticated assistant turns follow the server-authoritative architecture established in Batch 4B.2:

1. **Identity Resolution**: `assistant_chat` in `backend/app/main.py` extracts `current_user_id` strictly from the server-validated JWT/session via `get_current_user_id(authorization, db)` (never from request payload).
2. **Authoritative Repositories**:
   - `wardrobe_repo = WardrobeItemRepositorySQL(db)`
   - `user_state_repo = UserStateRepositorySQL(db)`
   - `saved_looks_repo = SavedLookRepositorySQL(db)`
3. **Canonical Use Case Instantiation**:
   ```python
   canonical_generate_outfit = GenerateOutfit(
       wardrobe_items=wardrobe_repo,
       user_state=user_state_repo,
       saved_looks=saved_looks_repo,
   )
   ```
4. **Dependency Forwarding**: `main.py` passes `canonical_generate_outfit`, `wardrobe_repo`, `user_state_repo`, and `current_user_id` into `engine.handle(...)`, which forwards them into `tools.recommend_outfit(...)`.
5. **Data Isolation**: Client wardrobe snapshots sent in the request body are strictly ignored; recommendations evaluate exclusively against the user's PostgreSQL wardrobe items.

### 5. Guest Execution Path

Guest assistant turns adhere strictly to Decision D10 Option A and the ephemeral adapters implemented in Batch 4B.1:

1. **Zero Database Access**: When `current_user_id is None`, zero SQL queries, database sessions, or transactions are executed.
2. **Ephemeral Repository Adapters**:
   - In-memory guest wardrobe items from request context hydrate `EphemeralWardrobeItemRepository(guest_items)`.
   - Guest preferences hydrate `EphemeralUserStateRepository(preferred_occasions=...)`.
3. **No Sentinel or Invented UUIDs**:
   - `derive_with_reason(user_id=None, ...)` and `EphemeralWardrobeItemRepository.get_for_user(user_id=None)` execute cleanly without fabricated UUIDs.
   - Original garment IDs (`"item-1"`, `"wire-top"`) are preserved exactly as provided by the client.
4. **Zero Appearance Persistence**: Any appearance keys injected into guest context are stripped by `EphemeralUserStateRepository`; `style_profile` remains empty (`{}`), and no appearance data is written anywhere.

### 6. Conversational Input Mapping

Assistant conversational signals map to `GenerateOutfitRequest` as follows:

| Assistant Signal | `GenerateOutfitRequest` Field | Recommendation Engine Treatment |
|---|---|---|
| `occasion` | `preferred_occasions: [occasion]` | Canonical scoring (+5.0 pts if matched), drives occasion match reason. |
| `preferred_item_ids` | `preferred_item_ids: [item_id]` | Canonical candidate filtering and scoring bonus (+5.0 pts). |
| `fit` | `fit: fit` | Canonical fit signal scoring (+5.0 pts if item silhouette matches). |
| `color_palette` | `color_palette: color_palette` | Canonical palette signal scoring (+5.0 pts if item color aligns). |
| `mood` | Contextual conversational parameter only | **Not scored**. Echoed or used conversationally, but zero points awarded in recommendation scoring. |
| `date`, `time`, `location`, `weather` | Not collected / Not sent | Ignored. Date and location are not automatically consumed by recommendation engine. |

### 7. Result Mapping

The canonical `DerivedOutfit` or `GenerateOutfitResult` maps to the assistant `SuggestionCard` model:

- **`id`**: Formatted as `"outfit-{rec.outfit_id}"` (or `"outfit-missing"` / `"outfit-empty"` for typed empty states).
- **`title`**: `rec.title` (canonical title, e.g., `"Casual Date Ensemble"` or `"Smart Casual Everyday"`).
- **`subtitle`**: Grounded reason string built from the first two canonical reasons:
  `". ".join(r.rstrip(".") for r in rec.reasons[:2]) + "."`
  (e.g., `"Picked for a Date occasion. Covers 2 categories: tops, bottoms."`).
- **`score`**: `int(round(rec.match_score * 100))` (derived dynamically from canonical `match_score`; `None` for empty/missing states). Never labeled as calibrated confidence or probability.
- **`components`**: List of string summaries of actual component garments:
  `f"{item.name} - {item.category}"`
  (e.g., `["Oxford Cotton Shirt - tops", "Slim Chino - bottoms"]`).
- **`action`**: `"open_outfit_builder"` for valid recommendations; `"open_wardrobe"` for empty or insufficient wardrobe states.

### 8. Error and Empty-State Handling

The assistant tool never fabricates an outfit when a valid recommendation cannot be derived:

1. **Empty Wardrobe (`EMPTY_WARDROBE`)**:
   - Condition: User has 0 wardrobe items in repository.
   - Response: Returns a typed `SuggestionCard` with `title="Wardrobe Empty"`, `score=None`, `action="open_wardrobe"`, and clear guidance to add garments before building an outfit.
2. **Insufficient Categories (`MISSING_REQUIRED_CATEGORY`)**:
   - Condition: Wardrobe lacks compatible combinations (e.g., tops only, no bottoms).
   - Response: Returns a typed `SuggestionCard` with `title="More Items Needed"`, `score=None`, `action="open_wardrobe"`, and explanation detailing the missing required category.
3. **No Valid Candidate (`NO_LEGAL_CANDIDATE`)**:
   - Condition: Garments exist but constraints or filters (e.g., conflicting preferred item ID) yield no legal pairings.
   - Response: Returns a typed `SuggestionCard` with `title="No Matching Outfit Found"`, `score=None`, explaining the constraint conflict.
4. **Database Failure (`DATABASE_FAILURE`)**:
   - Condition: PostgreSQL repository throws an unexpected database exception during authenticated execution.
   - Response: Catches error gracefully, logs the failure, and returns an honest `SuggestionCard` with `title="Service Temporarily Unavailable"`, `score=None`, prompting retry.
